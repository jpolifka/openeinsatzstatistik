# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

Einsatzstatistik für Feuerwehren (mandantenfähig): Einsatzbericht-PDFs aus dem BKS-Portal RLP einlesen, in SQLite speichern und die Auswertungen der früheren Excel-„Einsatzübersicht“ nachrechnen. FastAPI-Backend und eine Vanilla-JS-Oberfläche ohne Build-Schritt.

**Sprachkonvention:** Code ist **englisch** (Bezeichner, Funktionen, Module, DB-Tabellen und -Spalten, API-Pfade und JSON-Felder, CSS-Klassen, IDs). **Kommentare, Docstrings und alle Texte der Oberfläche sind deutsch.** Funktionsnamen beschreiben, was sie tun (`load_incidents`, `assign_vehicles`, `renderPreviews`).

## Befehle

Bevorzugt mit Docker arbeiten:

```bash
docker compose up -d --build          # bauen + starten → http://localhost:8112
docker compose logs -f                # Logs (u. a. Migration)
curl localhost:8112/health            # Health-Check (ohne Anmeldung erreichbar)
docker build --target test -t openeinsatzstatistik-test . && docker run --rm openeinsatzstatistik-test   # Tests (pytest)
docker run --rm openeinsatzstatistik-test python -m pytest -q tests/test_rbac.py -k <name>   # einzelner Test (nach dem Build oben; der Befehl ersetzt das CMD)
docker run --rm openeinsatzstatistik-test python -m pytest -q --cov=app --cov-branch --cov-report=term-missing:skip-covered   # Abdeckung (nur Python)
docker run --rm -v "$PWD/static:/s:ro" node:22-alpine node --check /s/app.js          # JS-Syntax
docker run --rm -v "$PWD:/w:ro" -w /w node:22-alpine node --test tests/frontend/*.test.cjs   # Frontend-Tests (wie CI)
```

`static/` ist nicht gemountet, sondern ins Image kopiert. Nach Änderungen an Python- oder Frontend-Dateien ist deshalb `--build` nötig.

Erfundene Testberichte (Excel-Export, wehrübergreifend, beliebige VG): `docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -e PYTHONUSERBASE=/tmp/pu -v "$PWD:/w" -w /w python:3.14-slim sh -c "pip install -q --user openpyxl && python tools/gen_test_reports.py <VG> <KENNUNG> [--wehren N] [--orte A,B] [--jahr J]"` → `Einsatzberichte/Test-<VG>/` samt `_Einrichtung.txt` (Einheit, Präfix, Fahrzeuge je Wehr für die Einstellungen). Kreiskennung per `--kreis` (Standard `NR#`; Kfz-Zeichen, `#` nur bei gleichem Zeichen von Stadt und Landkreis, OPTA).

Lokal ohne Docker: `DATA_DIR=daten uvicorn app.main:app --reload --port 8112`, Tests mit `pip install -r requirements-dev.txt && pytest`.

## Architektur

**Datenfluss beim PDF-Import (zweistufig):**
Jeder Endpunkt mit Einsatzdaten holt sich per `Depends(access)` ein `tenancy.Access` (Rechte des Benutzers, ausgewählte Wehr aus dem Cookie `scope`) und verlangt ein Recht aus `rbac` (`STATS`, `INCIDENTS`, `EXPORT`, `IMPORT`, `WRITE`, `DELETE`, `PEOPLE` …): `a.current(…)` für die ausgewählte Wehr bzw. `a.tenant(slug, …)` für eine bestimmte, Rechte auf VG-Ebene über `a.vg_can(vg_id, …)`. Fehlt es, wirft das `tenancy.Forbidden` (403). Gearbeitet wird nur mit `tenant.connection()` und `tenant.config`. Einsatz-IDs der API sind `"<slug>:<id>"`.

1. `POST /api/reports` (PDF oder Excel-Export `.xlsx`, einzeln oder als ZIP) → `importing.read_report`: `report.parser` wählt nach der Endung den Leser (`parse(unit_prefix)` → Bericht-Dict), Berichtsart erkennen (`report_kind`: Stammdatensatz / Haupt- / Nebenbericht, mit `bks_report_id` und `bks_record_id`). Stammdatensätze und Weiterleitungen werden ebenfalls nur als Vorschau vorgemerkt; keine Schreibzugriffe beim Lesen. Sonst wählt `report.match_tenant` die Wehr (Einheit, Fahrzeuge nur bei Wehren ohne `unit_marker`). Berichte einer anderen Wehr der VG (ohne Schreibrecht in der Auswahl) bekommen eine Weiterleitungs-Vorschau und gehen erst nach Bestätigung per `importing.forward` in deren `pending_report`; Berichte von Einheiten ohne Wehr (FEZ) werden als `notes` übersprungen. Danach `report.read` (`parse` → `complete_number` → `derive` → `check_plausibility`). Hochgeladene Dateien liegen als `importing.Spool` in einem Arbeitsordner (nicht im Speicher; je Upload höchstens 100 MB, gleichzeitig höchstens zwei, je Benutzer einer: `preview_sessions.UploadSlots`, sonst 429). Der Bericht liegt nur im Speicher (`preview_sessions.PreviewSessions`, TTL 1 h, daher nur ein uvicorn-Worker), gebunden an Benutzer und Wehr. Die Oberfläche liest mit `?background=true`: Die Anfrage antwortet sofort mit einem Job (`preview_sessions.ReadJobs`), gelesen wird parallel (`parser_worker.WORKERS`), Fortschritt und Ergebnis über `GET /api/reports/jobs/{job}` – lange Anfragen bricht der Proxy (Cloudflare, ca. 100 s) sonst mit 524 ab. `report.preview` liefert den Einsatz für die Vorschau mit Namensabgleich und dem bereits erfassten Einsatz (`store.find_existing`: gleicher BKS-Bericht, sonst gleiches `year` + `number`), `report.differences` die Abweichungen.
2. `POST /api/reports/accept` mit Token, Dateiname und vom Nutzer korrigierten `fields` → je Vorschau Stammdatensatz speichern, Bericht weitergeben oder `report.save`; mit `replace` und verpflichtender `revision` als Aktualisierung des erfassten Einsatzes (gleiche ID; `store.replace_report_rows` ersetzt Fahrzeuge und Anwesenheit aus dem Bericht, Zeilen mit `manual = 1` bleiben). Unbekannte Personen werden als neue `member`-Zeilen angelegt. Eine transaktionale Outbox mit minutengenauer Wiederholung ruft `importing.after_import` auf: Sie vermerkt den Bericht im zentralen Verzeichnis (`records.register_report`) und legt Hinweise an (`records.notify`, `records.notify_others`).

**Module (`app/`):**
- `domain.py`: Fachkonstanten, die **für alle Wehren** gelten (Funkrufnamenverzeichnis RLP mit `describe_call_sign`, Einsatzarten, Alarmstufen, Sonderstichworte B2.07/S1.00, Vorlage des Stichwortkatalogs) und Standardwerte für neue Wehren (Zeitgrenzen 10/15 Min., Tag 06–18 Uhr), Link ins BKS-Portal (`BKS_REPORT_URL`).
- `tenant_config.py`: `TenantConfig`, die **Fachkonfiguration einer Wehr** (Fahrzeuge als `Vehicle` mit Dienstzeitraum und vollem Funkrufnamen aus dem BKS-Bericht `name` – Zuordnung über `block_of`/`is_own`, `call_sign` ist nur der Kurzname des Blocks, ältere Einträge ohne Namen über `unit_prefix`; Ersatzfahrzeuge, BKS-Kennungen, Orte, Bedarfsplan-Orte, Zeitgrenzen, Stichwortkatalog, Nummerierung `numbering` „bks“/„by_date“ mit `store.renumber`, Freigabe `response_plan_public` – geprüft über `api.common.plan_visible`) mit den Regeln, die davon abhängen (`area_of`, `is_daytime`, `is_plan_relevant`, `substitute_label`). Sie wird als `cfg` durch `report`, `metrics`, `excel_export` und `api.common.incident_json` gereicht, nie als Modul-Global gelesen. Die Oberfläche bekommt sie über `GET /api/config` (`client_config`) und hält keine eigenen Kopien.
- `rbac.py`: Rollen und Rechte. `PERMISSIONS` (fester Rechtekatalog mit Gruppe, zulässigen Bereichen `vg`/`tenant` und Voraussetzungen), Rollen in der Zentral-DB (`role` mit `vg_id` NULL = System-/globale Rolle, sonst eigene Rolle einer VG; `parent_id` für Vererbung; `role_permission`; `role_grant` = Verteilung: wer welche Rolle vergeben darf; `role_event` nur anhängbar). `SYSTEM_ROLES` ist nur der Startbestand der Migration (`vg_lead`/`vg_stats`, `lead`/`editor`/`viewer`), `BKS_ROLES` die Funktionen des BKS-Portals in drei Stufen (Sachbearbeitung, Leitung, `vg_lead` als VG-Verwaltung mit AVV/Gebühren/Rollenpflege; erben nicht von `vg_stats`; `add_roles` setzt Systemrollen aus der Konstante neu, Migrationen `_add_bks_roles`, `_bks_role_tiers`: Stellv. Wehrführer/Wehrleiter, BKI, Sachbearbeiter, FEZ, Leitstelle; nie `SYSTEM_ROLES` erweitern – Schlüsselkollision beim Neuaufbau). **Aufgabenträger-Art:** `vg.kind` (`rbac.KINDS`: Verbandsgemeinde, kreisfreie Stadt, Landkreis, Leitstelle) und `role.kinds` (leer = überall); `Roles.visible` blendet Rollen aus, die zur Art der VG nicht passen (damit auch `find`, `grantable`, `grant`); Art ändern mit `tenancy.set_vg_kind` nur ohne unpassende Zuordnung. „Beteiligt/eigene“ des BKS ist strukturell: Wehr-Rolle = nur diese Wehr, VG-Rolle = alle Wehren der VG, kein Filter auf Einsatzebene. `Roles(con)` lädt alles je Anfrage (`permissions`, `grants`, `chain`, `find`, `visible`), `save_role`/`delete_role` prüfen die Leitplanken: VG-Rechte nur für VG-Rollen; `people.*` gilt für beide Bereiche (die Funktionsrollen und `vg_lead` haben es per Migration `_vg_lead_people`, `vg_stats` bewusst nicht), keine Zyklen. Keine Änderung an eigenen Zuordnungen bzw. an Rollen, die man selbst hat (`admin._not_self`, `admin._held`). Eine Rolle, die der Benutzer (auch über weitere Verteilung, `admin.roles._reachable`) selbst erreichen kann, darf nicht mehr Rechte enthalten als er hat oder erreicht (`admin.roles._check_ceiling`) – sonst eskaliert, wer nur Rollen pflegt.
- `tenancy.py`: Mandanten. Zentral-DB (`vg`, `tenant`, `account`, `membership` mit `role_id`, mehrere Rollen je Person und Bereich), Superadmins aus `ADMIN_EMAILS`. Eine VG-Rolle gilt in allen Wehren der VG; `Tenant.permissions` enthält nur Wehr-Rechte, `Access.vg_permissions` die der VG-Rollen, `Access.grantable` die vergebbaren Rollen. `access_for` baut das `Access`. **Vorgaben der VG mit Abweichungen je Wehr:** `load_config(con, name, layer)` führt `VgLayer` (Zentral-Tabellen `vg_setting`, `vg_keyword`; Schlüssel in `INHERITED`, u. a. `bks_code`) und die Wehr-Tabellen `setting` (nur Abweichungen und Werte aus `TENANT_ONLY`, u. a. `station`, `plan_places`), `fleet` und `keyword` (Abweichungen vom Katalog der VG, `merge_keywords`) zur `TenantConfig` zusammen; `save_config(con, cfg, layer)` speichert nur, was von der VG abweicht (gleich der VG = erbt). `lift_vg_defaults` hat die früher je Wehr gespeicherten Werte einmalig zur VG gehoben. Zwischengespeichert je Slug (`forget_config` bzw. `forget_vg_config` nach dem Speichern).
- `legacy.py`: `migrate_single_install`, die einmalige Übernahme von `DATA_DIR/einsaetze.db` als Wehr Altenau beim Start (nur Name, `legacy_config()`; Fahrzeuge, Kennungen, Orte und Logos stehen nicht im Code und werden nach der Übernahme in den Einstellungen angelegt). Die Fachkonfiguration der Tests steht in `conftest.CFG`.
- `records.py`: zentrale, personenfreie Daten über Wehren hinweg: Stammdatensätze (`master_record`), Verzeichnis der eingelesenen Berichte (`record_report`), Hinweise an Wehren (`notice`) und Prüfvermerke (`record_review`). `check` gleicht je Stammdatensatz die Wehren ab (Grundlage des Prüfprotokolls, Recht `VG_RECORDS`); dafür liest es die Wehr-DBs über `tenancy.vg_tenants` ohne Benutzerrechte und gibt nur personenfreie Befunde aus. Gemeinsame Einsätze erkennt `metrics.unique_incidents` über `bks_record_id` oder `dispatch_number`.
- `fees.py`: Gebührenordnungen je VG (`fee_schedule`, Fassungen mit `valid_from`) und `calculate` (Kostenersatz je Stammdatensatz über alle Wehren, nichts gespeichert). Fahrzeugtyp = `Vehicle.label`. Pflege mit `VG_FEES`, Berechnung mit `VG_RECORDS`. Werte der Satzung Bad Neustadt in `legacy.FEE_SCHEDULE_2024`.
- `pdf_report.py`: Text aus der PDF holen (`extract_text`) und auswerten (`parse_report`). Getrennt, damit Tests ohne PDF auskommen.
- `xlsx_report.py`: Excel-Export eines Berichts aus dem BKS-Portal (`read_workbook`, `parse_report`), liefert dasselbe Dict wie `pdf_report.parse_report` mit `source = "bks_xlsx"`. Nur ein Bericht je Datei (Unterblätter ohne Bericht-ID); die Spalten der Anwesenheitsliste sind gegenüber den Überschriften verschoben und werden am Inhalt ausgerichtet.
- `report.py`: Ableitungsregeln (Einsatzbeginn = früheste Alarmierung der eigenen Fahrzeuge `02/..`, EHF, Gerätehaus, Wochenende/Feiertag), Prüfhinweise und Umwandlung Bericht → Einsatz.
- `metrics.py`: rechnet die Excel-Formeln nach. Kommentare nennen die Excel-Spalten (AO = Azeit, AP = Ezeit, AR–AU = Stärken, AM = Gesamtstärke). Kennzahlen werden **nie gespeichert**. `evaluate()` berechnet sie einmal je Einsatz für `statistics`, `response_plan` und `attendance_overview`. Minuten laufen wie in Excel per Modulo 24 h ab Einsatzbeginn. Weitere Auswertungen aus den Berichtsangaben (alle aus `evaluate()`, nie gespeichert): `aborts` (Abbruchgründe, Gruppen über `domain.abort_kind`), `alarm_systems` (Brandmeldeanlagen je Nummer bzw. Objekt), `vehicle_usage` (alarmiert/ausgerückt/eingesetzt/nur bereit je Fahrzeug), `respiratory` (Atemschutz), `fire_course` (Zeit ab Eintreffen bis „Brand unter Kontrolle“/„Feuer aus“), `casualties`; `attendance_overview` zählt zusätzlich Funktionen und Atemschutz je Person. Alle melden Abdeckung („n von N“); **NULL = nicht angegeben, nie null** (Altdaten bekommen die Angaben erst durch erneutes Einlesen).
- `store.py`: Datenbankzugriff. `FIELDS` ist die Liste der bearbeitbaren Einsatzfelder; INSERT/UPDATE, das Pydantic-Modell in `api/incidents.py` und der Abgleich bauen darauf auf. `MemberDirectory` gleicht Namen über `names.NameMatcher` ab.
- `db.py`: Verbindungen (`connection(path)`) und **Migrationen**, getrennt für die Zentrale (`CENTRAL_MIGRATIONS`, `DATA_DIR/app.db`) und je Wehr (`TENANT_MIGRATIONS`, `DATA_DIR/tenants/<slug>/einsaetze.db`), gezählt über `PRAGMA user_version`. Schemaänderungen nur als neuen Schritt hinten anfügen. Wehr-Schritt 1 ist das ursprüngliche deutsche Schema, 2 benennt es ins Englische um, 3 ergänzt Konfiguration, Logos, Fahrzeuge, Stichworte und `dispatch_number`. Eindeutigkeit gilt über `(year, number)` je Wehr.
- `excel_layout.py`: `Layout`, der Spaltenaufbau der Einsatzübersicht aus der Fahrzeugliste einer Wehr (bei fünf Fahrzeugen A:AV). `excel_export.py` schreibt damit den Export mit Formeln wie im Original. Einen Excel-Import gibt es nicht mehr.
- `import_queue.py` (Outbox für `after_import`, in derselben Wehr-Transaktion wie das Speichern, idempotent), `tenant_lifecycle.py` (Wehr anlegen/archivieren wiederaufnehmbar: zuerst sperren, Auftrag speichern, erst nach dem Verschieben zentrale Zuordnungen entfernen; abgebrochene Anlagen landen in `deleted/incomplete-…`, nichts wird gelöscht), `request_limits.py` (Größenlimit je Weg schon beim Multipart-Lesen: JSON 2 MB, nur `UPLOAD_ROUTES` größer), `parser_worker.py` (PDF/XLSX in kurzlebigen Prozessen, max. 2 gleichzeitig, 45 s, CPU-/Speicherlimits; auch für Excel-Kataloge der Verwaltung), `bks_common.py` (formatunabhängige BKS-Regeln für PDF und Excel), `incident_schema.py` (gemeinsamer Feldkatalog).
- **Revisionen:** `PUT`/`DELETE` auf Einsätze verlangen `revision` (fehlt → 428, zwischenzeitlich geändert → 409); `store.renumber` erhöht betroffene Revisionen. Migrationen sind append-only, ein neueres Schema verhindert Downgrades absichtlich.
- `names.py`, `timeutil.py`, `holidays.py`: Namensvergleich, Zeitumwandlungen, Feiertage RLP.
- `mail.py`: Versand per SMTP (`SMTP_*`) über das Postfach der eigenen Domain, Envelope-From = `MAIL_FROM` (SPF), eigene DKIM-Signatur (`DKIM_SELECTOR`, `DKIM_KEY_FILE`, d = Domain aus `MAIL_FROM`) für DMARC; `python -m app.mail dkim-key|check|test`. Kein Dritt-Dienst.
- `auth.py`: Anmeldung per Magic Link (aktiv, wenn `ADMIN_EMAILS` gesetzt ist, sonst startet die App nur mit `AUTH_DISABLED=1` für die lokale Entwicklung; berechtigt ist, wer `tenancy.is_allowed`): Versand über `mail.py`, HMAC-signierte Links (15 Min., einmalig) und **serverseitige Sitzungen** (Tabelle `session` der Zentral-DB, 30 Tage; das Cookie ist ein Zufallswert, gespeichert nur als SHA-256; `create_session`/`end_session`, Logout löscht die Zeile). Superadmins sehen und beenden Sitzungen unter `/api/super/sessions` (Reiter Einstellungen → Sitzungen, nie die eigene). **Anmeldecode** als Alternative zum Link (`login_code` in der Zentral-DB, 8 Ziffern nur als HMAC, 5 Fehlversuche je Code, 10 je Adresse und Stunde über `login_failure`; Code und Link entwerten sich gegenseitig; `POST /auth/code`). Anmeldeseiten als `APIRouter`. Schlüssel (nur für die Links) aus `SECRET_KEY` oder `session.key` im Datenordner.
- `login_mail.py`: Anmeldemail im Design der Wehr (`tenancy.mail_tenant` = „First Hit“: älteste direkte Wehr-Zuordnung, sonst erste Wehr der ältesten VG-Zuordnung, sonst neutral); feste Hex-Farben aus `theme.palette`, Logo als `cid:`-Bild (`mail.build(images=…)`), Code als reine Ziffernfolge. Fehler in der Gestaltung fallen auf die neutrale Mail zurück.
- `theme.py`: Farben und Logos. `palette` leitet aus `colors` (`brand`, optional `brand_dark`) alle `--brand-*`-Tokens ab und dunkelt abgeleitete Töne selbst bis zum Mindestkontrast ab; `check` lehnt zu helle Farben ab; `image_type` erkennt PNG/JPEG/WebP am Inhalt (kein SVG). `NEUTRAL` gilt für Anmeldung und VG-Gesamtansicht.
- `admin/` (Paket, ein Modul je Thema: `overview`, `settings`, `vg`, `keywords`, `users`, `roles`, `superadmin`, gemeinsames in `common`; `admin/__init__.py` setzt den `router` zusammen): Verwaltung als `APIRouter` (`/api/admin/...` je Recht: `SETTINGS`, `PLAN_RELEASE`, `KEYWORDS`, `VG_FEES`, `USERS_*`, `ROLES_MANAGE`; `/api/super/...` nur Superadmin): Einstellungen einer Wehr (`SettingsIn` → `_check_settings` → `TenantConfig`, Meldungen auf Deutsch als 422) und Vorgaben der VG (`/api/admin/vgs/{vg}/settings`, Recht `SETTINGS` über `a.vg_can`), Fahrzeuge aller Wehren der VG (`/api/admin/vgs/{vg}/fleet`), Logos, Stichwortkatalog von VG bzw. Wehr über `_Catalog` (Import CSV/XLSX), Zuordnungen nach `Access.grantable`, Rollen (`/api/admin/roles`), Rechte einer Person mit Herkunft (`/api/admin/users/effective`), Protokoll (`/api/admin/role-events`), VGs und Wehren. Nach dem Speichern immer `tenancy.forget_config(slug)`.
- `dpa.py`: AVV je VG (`APIRouter`), Rechte `DPA_VIEW`/`DPA_EDIT` über `rbac.member_permissions` (auch bei gesperrter VG). Status `pending`/`draft`/`revoked` sperrt die Wehren der VG für alle außer Superadmins (Prüfung in `tenancy.access_for`, Liste in `Access.blocked`). Vertragstext aus `templates/avv_v<TEMPLATE_VERSION>.html`; **Textänderungen nur als neue Datei mit erhöhter `TEMPLATE_VERSION`**, damit gespeicherte Prüfsummen nachvollziehbar bleiben. Uploads nach `DATA_DIR/avv/<vg>/`, nie überschreiben; `dpa_event` ist per Trigger nur anhängbar.
- `feedback.py`: `POST /api/feedback` (`APIRouter`), schickt Nachrichten aus der Oberfläche per `mail.send` an alle `ADMIN_EMAILS` mit `Reply-To` des Absenders; nichts gespeichert, je Benutzer eine Nachricht pro 30 s. Aktiv nur mit Anmeldung und SMTP (`config.feedback`).
- `main.py`: Anwendung: Anmeldeprüfung als Middleware (`PUBLIC_PATHS` ohne Anmeldung), Oberfläche, Theme, `/api/config`, Auswahl der Wehr. `api/` enthält die Endpunkte mit Einsatzdaten als `APIRouter` (`evaluation`, `incidents`, `reports`, `records`, `export`; `common`: `access`, Einsatz-IDs, `incident_json`, `previews`/`read_jobs`, Filter der Gesamtansicht). `importing.py` ist das Einlesen der Berichte ohne HTTP (`read_report`, `read_files`, ZIP, `forward`, `after_import`, `preview_json`).

**Übungsdienste:** `trainings.py` + `api/trainings.py` (`/api/trainings`, Rechte `TRAININGS`/`TRAININGS_EDIT`, Rolle `trainer` in `BKS_ROLES`, Migrationen `_add_trainings` (Wehr) und `_add_training_roles` (Zentrale)). Eigene Tabellen `training`/`training_attendance` (nie in `incident`/`attendance`), damit Übungen **nie** in `metrics`, Auswertungen, VG-Gesamtansicht, `records` oder `unique_incidents` einfließen; gemeinsam ist nur der Personenstamm `member` (`active` = false blendet Ausgeschiedene nur in der Teilnehmerwahl aus; Namensabgleich beim Import nutzt weiter alle). Revisionen wie bei Einsätzen (428/409). Excel-Export: Blatt „Übungen“ nur mit Recht `TRAININGS` (`write_workbook(…, trainings=…)`). Frontend: `trainings.js` (nach `app.js`): Erfassen im Dialog `#training-dialog` über den einen Knopf `#btn-training` im Kopf (neben „Bericht einlesen“, kein Reiter bei Einsätzen); Liste der Übungen (aufklappbar, Bearbeiten im Dialog) als Ansicht `trainings` im Hauptreiter Einsätze, Teilnahmen je Person (aufklappbar, Balken) als `training_members` im Hauptreiter Personal. Der Personenstamm wird **nicht** dort gepflegt, sondern in Einstellungen → Personen (`admin/people.py`, Recht `SETTINGS` = Wehrführung, nicht der Erfasser: Anlegen, Umbenennen, ausgeschieden, Zusammenführen `merge`, Wehrwechsel `transfer` innerhalb der VG, Hinweise auf ähnliche Einträge). **QR-Anmeldung** (`checkin.py`, öffentlich ohne Benutzerkonto): Der Link ist nur ein dauerhafter Bearer ohne Wirkung allein. Nötig ist die PIN der Übung (`training.checkin_pin`, beim Anlegen erzeugt, bis zum Neuerzeugen gültig; legt nie eine Übung an); Eingaben landen in der Warteschlange `training_checkin` (Quarantäne) und erreichen `member`/`training_attendance` erst über `trainings.accept_checkins` durch die Übungsleitung (`TRAININGS_EDIT`). Falsche PINs zählt `setting.checkin_fails` je Wehr und Tag dauerhaft (`MAX_PIN_FAILS`), Obergrenze `MAX_QUEUE` je Übung. PIN und Warteschlange liefert `trainings.load` nur mit `with_checkin=True` (nie an Betrachter oder in den Excel-Export). Neue Auswertung nie aus `training*` speisen, ohne sie ausdrücklich getrennt zu halten (Garantietest `tests/test_trainings.py::test_trainings_never_enter_evaluations`).

**CSA und Protokoll:** CSA = `member.csa` (Kennzeichnung unter Einstellungen → Personen, Recht `SETTINGS`, jede Änderung über `audit.audit` als `csa.set`/`csa.unset` in `audit_event`, nur anhängbar, ohne Werte), `training.csa_load` = CSA-Belastungsübung; `trainings.csa_status` zeigt je Jahr, wer sie absolviert hat. Die Stellvertretung (`deputy_lead`) hat `agt.evaluate` direkt (nicht vererbt, `AGT_EXPECTED`). Eine Signatur von Einsätzen/Übungen gibt es nicht (Migrationen `_add_agt_cosign`, `_drop_sign_permission` haben sie entfernt); abgezeichnet werden Atemschutz-Einträge (siehe unten).

**Atemschutz-Dokumentation (persönlich):** `atemschutz.py` + `api/atemschutz.py` (`/api/atemschutz/me/…`, `/api/atemschutz/summary`, `/api/atemschutz/cosign`), `agt_reminders.py`, Frontend `atemschutz.js`. Importdarstellung und -zustand liegen in `imports.js`; Verwaltungsdarstellung in `admin_views.js`, Aktionen und Zustand in `admin.js`. Diese werden **vor** `app.js` geladen und enthalten nur Deklarationen (nichts am Seitenaufbau beim Laden, `$` & Co. erst zur Laufzeit); `VIEWS` in `app.js` verweist auf ihre Funktionen. Ansichten erzeugt `app.js` bzw. diese Dateien als Template-Strings mit `esc()` für Nutzerdaten. Der Zustand liegt im globalen Objekt `state`, die Fachkonstanten in `config` (von `/api/config`). Ansichten sind in `VIEWS` registriert (Reiter, Laden, Zeichnen); `records.js`, `admin.js` und `dpa.js` tragen sich nach `app.js` selbst ein. `app.js` meldet `app:data` (Daten neu geladen) und `app:view` (Ansicht gezeichnet) als Ereignisse auf `document`. Routing über den URL-Hash (`#evaluation`, `#incidents`, `#members`); Filter und Sortierung der Einsatzliste stehen als Parameter darin (`#incidents?cat=B&month=3`, `parseHash`/`applyListParams`/`syncHash`, Filter aus der Auswertung in `LIST_FILTERS`, Links per `listLink`). Ungespeicherte Einsatz-Bearbeitung schützt `confirmLeaveEdit`; Löschen läuft verzögert mit „Rückgängig“ (`pendingDeletes`). Tastenkürzel stehen am Ende von `app.js` und in `help.js` (`sec_shortcuts`). Tooltips kommen generisch über `data-tip`. `help.js` ist die **einzige Quelle für die Online-Hilfe**: `HELP_SECTIONS` liefert das Hilfefenster, Schlüssel sind die Feld- bzw. Kennzahlnamen der API. Es gibt **eine gesammelte Hilfe, keine `?`-Symbole an Feldern und Kennzahlen** (bewusst entfernt; neue Felder bekommen kein eigenes Symbol, nur einen Eintrag dort). Das `?` im Kopf öffnet die Hilfe kontextabhängig (`helpContext`): offener Dialog, sonst `VIEWS[…].help` der Ansicht (Abschnitt `sec_…` oder Feldschlüssel). Neue Ansichten bzw. Verwaltungsbereiche (`ADMIN_HELP` in `admin.js`) tragen dort ihren Hilfe-Schlüssel ein. Das Hilfefenster hat die Reiter Hilfe, Neuigkeiten und Feedback. `changelog.js` (`CHANGELOG`, neueste Version oben, Texte für Anwender ohne Technik) wird vor `help.js` geladen; **sichtbare Änderungen bekommen dort einen Eintrag**. Für „ungelesen“ (Markierung am `?`) zählt das optionale Feld `version` eines Eintrags (z. B. `"2026-10-14.2"`), sonst das Datum; gespeichert wird die Version des neuesten Eintrags. Kommt am selben Tag ein weiterer Eintrag dazu, bekommt er eine `version` mit Suffix (`.2`, `.3` …), die als Text größer ist als das reine Datum – bestehende Einträge brauchen keine. Texte mit Werten der Wehr (Fahrzeuge, Orte, Zeitgrenzen) sind Funktionen, die zur Laufzeit aus `config` lesen – keine festen Zahlen oder Namen. `help.js` wird vor `app.js` geladen und nutzt dessen `$` und `esc` erst zur Laufzeit. `admin.js` (Verwaltung) und `dpa.js` (Auftragsverarbeitung) werden nach `app.js` geladen und tragen sich in `VIEWS` ein (`visible()` statt `permission`); Eingaben binden über `data-bind="pfad"` an `admin.settings`. Rechte im Frontend sind die Schlüssel aus `rbac.PERMISSIONS` (`can("incidents.view")` für die Auswahl, `config.vg_permissions` für die Gesamtansicht, `config.admin` für die Verwaltung); `ADMIN_SECTIONS` nennt je Bereich das nötige Recht. Jedes Recht hat in `help.js` einen Eintrag `perm_<schlüssel mit _>`.

**Einsatz bearbeiten:** `PUT /api/incidents/{key}` benötigt `revision` und nimmt neben den Feldern optional `vehicles` und `people` (`store.replace_vehicles`, `store.replace_attendance`); neue Zeilen bekommen `manual = 1`. Im Frontend hält `state.editDraft` die Anwesenheit bis zum Speichern; `openIncident(key, year)` springt zu einem Einsatz in der Liste.

**Neues Einsatzfeld:** Migration in `db.py` (`TENANT_MIGRATIONS`), Eintrag in `incident_schema.FIELDS` (ggf. `INT_FIELDS`; nur im Bericht angegebene Werte als `OPTIONAL_TEXT`/`OPTIONAL_TIMES`/`OPTIONAL_COUNTS`: leer = nicht angegeben; in `store` importiert), Lesen in `pdf_report` **und** `xlsx_report`, Ableitung in `report.derive`, ggf. `report.COMPARED_FIELDS`, `FORM_FIELDS` in `incident_schema.py` (per `/api/config` an das Frontend), Hilfetext in `help.js`.

## Betrieb

- Container läuft nie als root, sondern als Besitzer von `./daten` (`docker-entrypoint.sh`; `APP_UID`/`APP_GID` übersteuern). Der Port ist standardmäßig an `127.0.0.1` gebunden, anderes nur über `APP_BIND`. Eine öffentliche `BASE_URL` verlangt `ADMIN_EMAILS`.
- Qualität: Ruff (`ruff.toml`, schlank: E4/E7/E9/F/B; lokal `docker run --rm -v "$PWD:/w" -w /w python:3.14-slim sh -c "pip install -q ruff==0.17.6 && ruff check app tools tests"`), Mindestabdeckung 95 % (Zeilen und Zweige, steht im `CMD` des Test-Images), CodeQL (`.github/workflows/codeql.yml`, Python und JavaScript, wöchentlich und bei Push/PR).
- Abhängigkeiten: `requirements.txt` → `requirements.lock` mit SHA256-Hashes (Image installiert mit `--require-hashes`); beim Ändern das Lock neu erzeugen. CI (`.github/workflows/checks.yml`) prüft Python 3.14 (wie das Image; 3.15 scheitert noch an fehlenden Wheels für httptools und pydantic-core), Lock, Sicherheitsaudit, JS-Syntax und Frontend-Tests.
- Sicherung: Zentral-DB, **alle** Wehr-DBs, Assets und AVV-Dateien als konsistenten Bestand sichern, nicht einzelne SQLite-Dateien bei laufenden Schreibern kopieren. Vorschauen liegen im Speicher eines Workers (keine horizontale Skalierung ohne gemeinsamen Speicher).

## Daten und Datenschutz

`Einsatzberichte/` (PDFs, Excel) und `daten/` (SQLite) enthalten Namen und Anwesenheiten. Sie sind per `.gitignore` ausgeschlossen und dürfen nicht eingecheckt werden. Auch im Code und in Tests keine echten Namen verwenden (Beispiele: „M. Muster“, „Beispiel, Erika“). Konfiguration: `.env` (Vorlage `.env.example`: `APP_PORT`, `BASE_URL`, `ADMIN_EMAILS`, `SECRET_KEY`, `SMTP_*`, `MAIL_FROM`, `DKIM_*`, `DPA_*` für den AVV). Neue Variablen gehören immer mit Kommentar in `.env.example`. Tests prüfen die Rechte als Matrix (`tests/test_access.py`), Rollen, Vererbung und Leitplanken in `tests/test_rbac.py`; neue Endpunkte mit Einsatzdaten gehören dort hinein. Ein neues Recht: Eintrag in `rbac.PERMISSIONS`, Zuordnung zu Systemrollen per Migration (nicht über `SYSTEM_ROLES`, das nur der Startbestand ist), Hilfetext `perm_…` in `help.js`.
